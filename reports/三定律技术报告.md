# 三定律与场景预算：DeepSeek 前缀缓存的应用侧编排实测

AI 辅助声明见 [AI_DISCLOSURE.md](../AI_DISCLOSURE.md)。全部数据可由仓库内脚本独立复现。

## 摘要

DeepSeek API 提供自动前缀缓存（命中输入约为未命中价格的 2%），但官方文档未给出缓存行为的定量刻画，应用侧普遍缺乏可操作的命中率工程方法。本文在真实 API 上做了一组受控实验（约 750 次调用、累计 ~2150 万输入 token，总成本约 $1.1，估算口径见 §5.3），提出三条经验定律（滞后窗定律、块级匹配、账号级跨会话复用），据此实现了一个三区会话编排库（CacheCortex），并在终端编程式负载上实测稳态输入命中率 **98.3%~99.8%**（随分母规模变化，与公式预测一致）。同时给出覆盖 11 类典型负载的命中率预算模型，作为应用侧的容量规划工具。本文不声称提出新的缓存机制——机制属于服务端；贡献是把"客户端可观测、可预测、可编排"的部分形式化并给出实测边界。

---

## 1. 背景与动机

DeepSeek 的自动前缀缓存按 token 级前缀匹配计费（命中价约为未命中价的 1/50），社区已有工程实践（如 Reasonix 报告的 99.82% 单日命中率），但存在三个空白：

1. **机制缺乏定量刻画**：匹配粒度、最小可缓存长度、时效、跨会话行为均无公开实测；
2. **命中率缺乏预测模型**：开发者只能事后看账单，无法在构建前回答"我的场景能到多少"；
3. **实践未形式化**：有效的工程纪律（三区结构等）散落在教程与项目文档中，没有可复用的库与回归测试。

本文依次填补：§3 三条定律（受控实验）；§4 编排库设计与实现；§5 同负载对标与 11 场景预算表；§6 边界与限制。

## 2. 实验设置

- 端点：DeepSeek API（OpenAI 兼容与 Anthropic 兼容两个路径均测）
- 模型：deepseek-flash
- 全部实验为串行小规模调用（单次 ≤ 20 万 token），总成本约 $1.1（估算口径见 §5.3）
- 命中率口径：`hit / (hit + miss)`，hit/miss 取自响应 usage（prompt_cache_hit_tokens / prompt_cache_miss_tokens）
- 脚本与原始数据随仓库附带（benchmarks/ 与 results/）

## 3. 三条经验定律

### 定律一：滞后窗定律

append-only 会话中，最近一次生成的内容在下一轮请求时**尚未进入缓存**，形成固定大小的"滞后窗"（实测 128~256 token，跨 4 个规模点恒定）。稳态输入命中率为：

```
命中率 ≈ 1 − 滞后窗 / 该轮总输入
```

实测验证（4 个规模点，均为 30~300 轮 append-only 会话）：

| 规模点 | 总输入 | 实测命中率 | 公式预测 |
|---|---|---|---|
| A（1.7K） | 1,771 | 86.7% | 86.7%（235 tok 滞后） |
| B（6.3K） | 6,300 | 98.29%（尾段） | ~98.3% |
| C（19.8K） | 19,765 | 99.08%（末轮） | 99.08%（181 tok 滞后） |
| D（103K） | 103,103 | **99.81%** | 99.81%（191 tok 滞后） |

**工程含义**：immutable prefix（会话内冻结的稳定前缀）越长越好——滞后窗固定，分母增长直接转化为命中率。这解释了为何编程类 Agent（单轮上下文数万 token）能把命中率做到 99.8%+。

### 定律二：块级匹配

前缀按 **64-token 块**粒度匹配：
- 实测命中数总为 64 的倍数（1536=24×64，640=10×64，两处独立证据）；
- 前缀中部改动一个字，命中数不归零，而是截断到块边界（比"一字全断"的直觉宽松）；
- **不足 64 token 的 prompt 从未产生命中**（20 token 的 prompt 重复 16 次全部 miss）——自我一致性采样等短 prompt 重复场景没有缓存红利，除非把共享说明前缀化加长。

### 定律三：账号级跨会话复用

缓存按账号共享，跨进程、跨会话存活数小时：
- 同序列会话重跑，第二轮起命中上一会话留下的缓存（对照组污染事故的正面利用）；
- 预热请求（max_tokens=1 的最小调用）本身命中前一会话的缓存 97~99.7%；
- 工程含义：对照实验须加随机 nonce 隔离历史缓存；生产中重启应用不丢命中率。

### 附：反模式（前缀污染）

前缀区含动态内容（时间戳/计数器/运行时变量）时，命中率从 ~99% **断崖式降至 0%**（每轮前缀从污染点起全部分歧）。这不是线性衰减——污染必须归零，任何后续优化都以它为前提。

## 4. CacheCortex：三区编排库

按上述定律实现的应用侧编排层（MIT，Python，核心零依赖）：

- **PrefixBankSession**：三区会话状态机（Immutable Prefix / Append-Only Log / Dynamic Tail），SHA-256 指纹回归测试，逐次 hit/miss 记账，ReadTracker（会话读集合），缓存友好折叠（summary 追加而非重写），预热接口（消灭冷启动 miss）
- **CacheTiers**：provider 能力探测（两次同前缀请求看 usage 字段）→ 三层策略（自动前缀缓存 / 显式标记注入 / 响应缓存兜底）
- **hitrate_budget**：场景预算器——输入前缀/尾巴/轮数参数，输出命中预测与到 95% 的杠杆建议（内置 11 类负载模板）
- **optimize_stack**：场景 → 杠杆组合（审计 / 前缀库 / 尾部压缩 / 调度 / 降级）

六项单测 + 两种基准模式（模拟/真实），`pip install -e .` 后三行代码出命中率曲线。

## 5. 同负载对标与 11 场景预算表

### 5.1 与已公开方案的同负载对比

终端编程式负载（immutable prefix ≈ 6K tok，每轮 user ≈ 200 + assistant ≈ 300 tok）：

| 方案 | 负载 | 稳态命中率 |
|---|---|---|
| Reasonix（公开报告，2026-05-01 单日） | 生产编程会话（单日 4.36 亿 tok） | 99.82% |
| 本文三区纪律（120 轮，6.3K 分母） | 模拟编程负载 | 98.29% |
| 本文三区纪律（300 轮，19.8K 分母） | 同上延长 | 99.08%（末轮） |
| 本文三区纪律（100 轮，103K 分母） | 大分母版 | **99.81%** |

按滞后窗定律，两者差异由**负载的分母规模**解释（Reasonix 生产会话单轮上下文数万 token，分母大 1~2 个数量级），而非机制差异：分母归一后两者落入同一区间。本方案的差异化在于**机制无关的多 provider 支持**（探测分层覆盖 Anthropic/Gemini 路径）与**预热接口**（消灭冷启动 miss，实测轮 1 命中从 0% → 96.7%）。

### 5.3 成本

官方逐小时账单（usage_data CSV 导出）：deepseek-flash 缓存实验部分共 809 次调用、命中输入 2236 万 tok、未命中 135 万 tok、输出 6.5K tok，实际花费 **¥1.83（≈$0.26）**。官方单价（官方定价页 + 账单 price 列双证）：deepseek-flash 命中 off-peak $0.003/M（peak $0.006）、未命中 off $0.15/M（peak $0.30）、输出 off $0.6/M（peak $1.2）——注意部分公开资料引用的"输出 $0.28"为旧价或误引。**Off-peak 定义**（官方文档原文）：peak 为工作日（周一至周五）UTC 01:00-04:00 与 06:00-10:00，**中国法定节假日全天按 off-peak 计**——本实验（2026-10-02/03，国庆假期）全程享受 off-peak 价，与账单单价恒定的观察一致。

## 6. 边界与限制

1. **单 provider**：全部实测在 DeepSeek API 上。三定律中的块粒度（64 tok）与时效为该 provider 特性，其他 provider 的映射（OpenAI 1024 门槛、Anthropic 显式标记）来自文献而非本文实测；CacheTiers 的探测分层设计即为此保留。
2. **模拟器的地位**：模拟对标中的 SimulatedDeepSeek 按本文实测机制建模，用于验证编排逻辑自洽；其结果不构成对真实 provider 的新证据。真实 API 数据以标注 live 的运行为准。
3. **负载为合成**：11 场景的参数（前缀/尾巴/轮数）来自公开报告与合理估计，非逐场景实测；预算器输出是设计参考而非承诺。
4. **单日快照对比的口径问题**：Reasonix 99.82% 为单日累计口径（含冷启动摊薄），本文对比时按"分母归一"原则解释差异，不构成对其数字的复核。
5. **量级限制**：单会话最长 300 轮、最大前缀 90K tok；更大规模（百万级 token/日）的行为未测。
6. **输出 token 永远全价**：本方法只优化输入侧；输入占比低的任务（如短输出实验）收益有限——这恰恰是本文实验场景自身的情况，参见《思考外挂阶段 0 报告》的成本分析。

## 7. 结论

DeepSeek 前缀缓存的命中率在应用侧是**可预测、可编排、可回归测试**的工程量：三定律给出预测模型，三区结构给出实现，预算器给出容量规划。在 103K 分母的终端编程式负载上，本文方法实测 99.81%，与已公开的最佳工程实践（Reasonix 99.82%，生产规模）处于同一水平——且以通用库形式提供，附场景预算器与跨 provider 探测分层。

后续工作：多 provider 实测（OpenAI/Anthropic 原生）、尾部压缩集成（LLMLingua 类）、非英语 token 化下的块粒度复核、以及把预算器扩展为在线反馈控制器。
